6.8.1. 1. 从 wl_shm_buffer 转换为像素数据

如果客户端通过 wl_shm 发送 wl_buffer，该缓冲区存储在共享内存中，通常以 WL_SHM_FORMAT_ARGB8888 或类似格式提供。可以通过 wl_shm_buffer_get() 获取共享内存缓冲区，并从中提取像素数据。

6.8.3. 3. 其他方式：通过 EGL 或 OpenGL 读取像素

对于通过 EGL 发送的 wl_buffer，如果你已经设置了 EGLContext，你可以使用 glReadPixels() 函数从 EGL 表面读取像素数据。

6.8.4. 总结

  • wl_shm_buffer：通过共享内存发送的缓冲区，可以直接访问内存中的像素数据。
  • GBM/EGL buffer：需要通过 gbm_bo_import 导入 wl_buffer，然后通过 gbm_bo_map 映射到 CPU 可访问的内存，才能读取像素数据。

  • 如果只使用 CPU 画图，可以直接修改 DMA Buffer 中的数据，特别是在没有使用 GPU 加速的情况下。
  • 如果使用 GPU 加速，CPU 通常用 DMA Buffer 与 GPU 共享数据，而 GPU 会负责图形的实际渲染，CPU 则负责准备数据。

7.9.11. 1. 什么是 AFBC？

AFBC 是 Arm Mali GPU 和显示处理器 (DPU) 中广泛使用的一种压缩技术：

  • 它将帧缓冲的数据以一种块状压缩格式存储，每个块可以单独解压缩。
  • AFBC 通常在硬件渲染和显示链路中使用，CPU 并不直接理解这种压缩格式。

7.9.12. 2. AFBC 对 CPU 操作 DMA 缓冲区的影响

a. 数据的压缩格式

AFBC 使用压缩存储数据，因此当 DMA 缓冲区启用了 AFBC 时，CPU 无法直接以常规的方式（例如像访问普通像素数据那样）操作它。压缩的格式需要通过硬件或专门的解码器来解码。

  • 如果 CPU 操作启用了 AFBC 的 DMA 缓冲区内容，很可能导致数据损坏或产生无法预期的结果。
  • CPU 对 AFBC 数据的操作通常需要进行解码和重新编码（解压后修改，再压缩存储），这会引入额外的开销。

b. 数据对齐和块布局

AFBC 的数据是按块对齐存储的，每个块都有特定的元数据（Meta Data），描述了该块的像素数据压缩情况。因此，即使 CPU 能访问到内存区域，也需要解码元数据和块数据的结构才能正确理解和修改内容。

7.9.13. 3. 如何处理 AFBC DMA 缓冲区？

如果你的系统启用了 AFBC，并且你希望通过 CPU 操作 DMA 缓冲区，有以下几种方法：

a. 禁用 AFBC

如果你需要 CPU 直接操作 DMA 缓冲区，可以禁用 AFBC，这样帧缓冲就会以未压缩的格式存储。通常可以通过以下方式禁用：

  • 在分配帧缓冲时，明确指定不启用 AFBC。例如，使用 DRM Dumb Buffers 通常默认不会启用 AFBC。
  • 修改相关驱动程序的设置，要求帧缓冲输出为未压缩格式。

b. 使用 GPU 或硬件进行操作

如果 AFBC 必须启用，建议使用 GPU 或其他硬件来完成需要的绘图或数据修改操作，因为它们能够直接理解和操作 AFBC 格式的数据，而不会产生数据错误。

c. 解压缩后操作

在某些场景下，你可以将 AFBC 格式的帧缓冲解压缩到 CPU 可操作的平面（Plane）格式，完成修改后再重新压缩为 AFBC 格式。这通常需要 GPU 或其他硬件支持。例如：

  • 使用特定的 API（例如 OpenGL 或 Vulkan）将 AFBC 数据解码到标准的 RGBA 格式供 CPU 操作。
  • 完成操作后，再通过 API 将数据重新压缩为 AFBC。

某些平台或驱动可能提供工具或库，用于直接访问和操作 AFBC 数据。检查你的硬件和驱动支持是否有这样的功能。

11.12. 带宽优化

11.12.1. 方案 A：对于“不透明”内容，使用 RGBX 或 RGB565

  • 场景：底图、全屏游戏、或者确定没有透明度的背景层。
  • RGBX8888：虽然还是占 32位，但硬件（Display Controller）知道不需要读取 Alpha 通道进行混合（Blending），可以省去合成阶段的 Alpha 乘法计算，甚至某些硬件能直接跳过 Alpha 位的读取（Masking）。
  • RGB565：每个像素占 16位 (2 Bytes)。
    • 带宽节省：直接 减半 (50%)。
    • 代价：色彩精度下降，会有色彩断层（Banding）。但在早期的低端车机或简单的仪表盘背景中常用。

11.12.2. 方案 B：对于“视频/摄像头”，强制使用 NV12/NV21 (YUV)

  • 场景：车载倒车影像、360环视、视频播放。
  • 原理：视频解码出来原数据就是 YUV 格式。
    • 错误做法：GPU 把 YUV 转换成 ARGB 纹理，再画到屏幕上。（带宽爆炸：读 YUV + 写 ARGB + 读 ARGB 上屏）。
    • 正确做法 (Direct Scanout)：直接把 NV12 (12-bit per pixel) 的 Buffer 给到硬件图层（Overlay Plane）。
  • 带宽节省：
    • NV12 只需要 1.5 Bytes/像素，对比 ARGB 的 4 Bytes/像素，带宽节省 62.5%。
    • 且省去了 GPU 的转换算力。

11.12.3. 方案 C：使用硬件帧缓冲压缩 (AFBC / UBWC) —— 这是高阶加分项

这是现代旗舰 SoC（高通 8155/8295, 瑞芯微 RK3588, MTK）最主流的带宽优化技术。

  • 概念：ARM 的 AFBC (Arm Frame Buffer Compression) 或高通的 UBWC。
  • 原理：GPU 渲染完画面写入内存时，是无损压缩存储的；Display Controller 读取显示时，是解压读取的。
  • 优化：
    • 虽然格式可能还是 ARGB8888，但实际传输和存储的数据量大幅下降（通常能压缩 30%-50%）。
    • 面试话术：“在带宽优化方面，我确保了 Graphics Pipeline 全链路启用了 AFBC 压缩。从 GPU 渲染目标配置到 Display 端的 Modifier 协商，确保 Buffer 始终以压缩格式流转，避免了不必要的解压和重压。”

使用gles2绘图的client的初始化过程大致是这样的：

  • client 先要通过本地窗口系统获得一个窗口，把它作为参数传入 eglCreateWindowSurface()，获得 EGLSurface, 类型为 window surface，位于GPU的VRAM中。
  • client 调用 eglMakeCurrent()，把 EGLSurface 和 EGLDisplay（通过 eglGetDisplay()得到，图中未画）绑定到一个 rendering context（通过 eglCreateContext()创建，图中未画）.
  • client 使用 gles2 函数绘图，所有的操作都作用在egl 提供的 rendering context上，最后调用 glDrawElements() 或 glDrawArrays()告诉GPU开始绘图。OpenGL ES 2 只支持double buffer, 所有所有绘图操作都作用于 back bufffer上。
  • client 调用 eglSwapBuffers()，切换 back buffer 和 front buffer 的内容，绘图内容呈现在显示器上。

gles2 中的几个copy像素的函数：

  • glTexImage2D()：把系统内存中存放像素的缓冲区拷贝到texture，System RAM => VRAM
  • glReadPixels()： 把color buffer的内容(来自back buffer)拷贝到系统内存, VRAM => System RAM
  • glCopyTexImage2D()： 把color buffer的内容拷贝到texture，VRAM => VRAM

22.1.2. 硬件图层plane

本质：硬件图层的层级

​ 最终来源： My chips have four independent H/W overlays.

硬件图层分类：

  • Primary Plane：主平面，主Overlay Plane。负责显示桌面或主画面。每个 CRTC（显示控制器）至少有一个 Primary Plane。
  • Overlay Plane：覆盖平面，负责显示叠加在主画面上的图像，比如视频播放窗口、硬件加速的图形层等。一个显示控制器可以有多个 Overlay Plane。
  • Cursor Plane：光标平面，专门用于显示鼠标指针。

软件的标识：

enum wdrm_plane_type {
    WDRM_PLANE_TYPE_PRIMARY = 0,  // 用于GPU的plane
    WDRM_PLANE_TYPE_CURSOR,
    WDRM_PLANE_TYPE_OVERLAY,  // 用于叠加的plane
    WDRM_PLANE_TYPE__COUNT   
};

注意： Overlay 是一种特殊的 plane，用于叠加显示额外的图像内容。

Plane 的使用

在实际使用中，开发者可以通过 DRM 的 API 来配置和操作 plane。以下是一个基本的步骤概述：

  1. 获取 Plane 信息：
    • 使用 drmModeGetPlaneResources 获取所有可用的 plane 资源。
    • 使用 drmModeGetPlane 获取具体的 plane 信息。
  2. 设置 Plane：
    • 使用 drmModeSetPlane 将图像数据设置到指定的 plane 上，并定义其在屏幕上的位置和大小。
